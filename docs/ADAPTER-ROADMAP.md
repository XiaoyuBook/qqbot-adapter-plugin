# QQBot 喵崽适配器开发路线

目标是让任何使用已声明喵崽接口的插件，都能按同一套规则识别用户、接收事件、发送消息并判断结果。开发按公共接口排期，具体插件作为这些接口的调用方参与验收。首个目标环境为 Miao-Yunzai 3.1.3、官方群聊和 C2C，与其他适配器共存。

## 适配器对插件的公共约定

入站从 QQ 事件取得账号、会话、发送者和原消息标识，生成喵崽事件并交给宿主。出站从插件的一次发送调用取得目标、消息元素和选项，验证平台能力，生成有序的发送步骤，再把结果交回调用方。同一账号、场景和权限下，两个插件作出相同的调用，应当得到相同的处理。

| 职责 | 所有调用方可以依赖的行为 | 现有实现落点 |
| --- | --- | --- |
| 连接与账号生命周期 | 出站网关处理鉴权、心跳与恢复。先注册账号再派发事件，重载或断开时只处理本账号的连接和注册状态。NapCat 与 QQBot 以任意顺序启动或恢复，都能通过各自账号收发。锅巴保存连接设置时保留私有凭据的只写语义。 | [连接](../src/transport.js) · [生命周期](../src/controller.js) · [账号注册](../src/accounts.js) · [锅巴](../guoba.support.js) |
| 身份、数据归属与权限 | 平台身份按 AppID 和场景区分。未关联用户有稳定的宿主标识，可信管理员核实的关联可供宿主读写既有用户数据。发给谁由平台联系人决定，谁能执行主人操作由授权策略决定。关联在重载后仍然生效，撤销后不再解析到原数据归属。业务数据的文件格式、合并与迁移由数据所有方负责。 | [身份](../src/identity.js) · [联系人](../src/accounts.js) · [事件](../src/events.js) |
| 宿主事件与联系人 | 在同一进程的去重窗口内，同一平台事件重复投递，业务只执行一次。明确 `e.bot`、`e.sender`、`e.group`、`e.member`、`e.friend` 及联系人查找方法在各场景的字段、方法和返回值。供插件探测的可选方法只有具备能力时才暴露。 | [事件转换](../src/events.js) · [账号与联系人](../src/accounts.js) · [群成员](../src/group.js) |
| 消息表达与顺序 | `e.reply` 和联系人 `sendMsg` 共用一套规则，接受喵崽的文本、元素、数组及显式转发节点。保留一次调用内的元素顺序和多次调用之间的边界。单条图文按约定排版。插件分两次调用时，两次回复分别进入发送队列。按钮、引用和转发按元素及显式选项解释。 | [回复](../src/reply.js) · [消息元素](../src/segment.js) · [转发](../src/forward.js) · [媒体](../src/media.js) |
| 投递、能力与回执 | 被动发送沿用触发它的账号、会话、原消息和额度。主动发送单独校验权限。回执区分全部成功、部分成功、明确拒绝及投递未知，并保留已成功段的消息 ID。发送前已知缺少能力，或平台明确拒绝投递时，可按约定降级并返回原因。投递结果未知时禁止自动重发。 | [事件上下文](../src/context.js) · [发送](../src/reply.js) · [平台 API](../src/api.js) · [错误](../src/errors.js) |

表中是目标约定。实施时每项分别标注当前实现和验证证据，已有实现可直接补证据，行为有差异才改代码。

0.2.8 首批实施见 [公共接口基线与探针](PUBLIC-CONTRACTS.md)：固定宿主群聊/C2C 共用探针，修复联系人可选探测、群成员归属、观察联系人列表与分段回执；后续能力依该表补充证据。

## 开发顺序与交付条件

| 阶段 | 交付物 | 完成条件 |
| --- | --- | --- |
| **一 · 建立兼容基线** | 首批对照 `Bot[self_id]`、`e.user_id`、`e.isMaster`、`pickGroup/pickFriend`、`e.reply`、`sendMsg` 和发送回执。逐项记录输入、返回、适用场景、上游依据、当前差异和测试。用一个无业务逻辑的探针插件走通“收事件 → 取联系人 → 回复 → 取回执”。 | 在固定版本的真实喵崽加载器中，群聊与 C2C 都能运行同一个探针。每项差异都有归属，能够区分宿主接口缺口、平台权限限制和插件自己的行为。[宿主测试入口](../test/host/harness.js) · [固定版本清单](../test/host/manifest.json) |
| **二 · 稳定身份与宿主接口** | 在现有身份、账号、事件入口统一正反向查找、权限判断、联系人行为和生命周期，再用真实宿主的数据读取入口验证标识如何传递。 | 测试覆盖未关联与已关联用户、撤销及重载、跨账号和群私聊隔离、NapCat 两种加载顺序、重连重放。任何一个调用方都可以复用同一组断言。 |
| **三 · 统一消息发送** | 在现有回复入口先将不同输入转换为统一的消息元素，再检查能力与额度、按序发送、汇总回执。`e.reply`、事件内联系人发送和显式主动发送复用消息转换，各自保留路由规则。 | 测试区分一次组合发送与两次独立调用，覆盖并发会话、多段发送、部分成功、权限拒绝及网络超时。替换插件名称、命令或文案后，路由、消息边界和失败处理相同。 |
| **四 · 按能力扩展与发布** | 媒体、Markdown、交互、撤回、群管理等按同一接口清单逐项交付。每项写明适用场景、所需权限、可用的替代形式，并分别记录宿主测试、实号 API 和客户端显示的证据。 | 发布前复跑公共契约，选择不同来源的实际插件抽验同一能力。可见排版在 QQ 客户端验收，随后按该版本的能力表更新公开使用说明。 |

## 新需求和已有修复怎样归类

- **公共接口有差异**　先用最小插件调用复现，写清预期输入、输出或时序，再修负责该规则的模块。原业务场景保留为集成回归。评审时检查核心逻辑能否仅依据账号、场景、消息元素、显式选项和平台结果作出决定。
- **平台能力受限**　把权限、额度和可接受的降级登记在能力表，同类调用共享处理。公开说明区分“代码已实现”“该账号获准使用”和“客户端已验收”。
- **业务插件决定了行为**　插件掌握业务含义以及何时调用发送接口。它若到任务结束才交出内容，适配器只能从这次调用开始投递。需要改变业务决定时，优先使用插件已有扩展点或向上游提交改动。确需兼容特定版本时，单独记录适用版本、启用条件和移除条件。具体插件和命令用于集成验收，核心发送逻辑依赖公共接口里可见的信息。
- **在途改动**　按以上三类复核。能用公共接口复现的部分归回对应阶段，特定插件的处理单独管理。后续版本据公共接口表选择缺口和验证范围。
